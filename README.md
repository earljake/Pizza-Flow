# PizzaFlow — Session 1: Foundations in In-Memory Cluster Compute

**MIT 261 — Parallel and Distributed Systems | Individual Capstone**

PizzaFlow is a transactional, order-driven revenue-intelligence pipeline over a
pizzeria sales dataset. Session 1 establishes the baseline: a validated
multi-file join, a partitioning strategy, a sequential (pandas) reference
implementation, a bounded-parallel (PySpark local) implementation, and a
benchmark comparing the two.

## 2. Dataset

Four related CSV files describe a pizzeria's order history:

| File | Role | Rows | Primary Key | Foreign Key(s) |
|---|---|---|---|---|
| `orders.csv` | Event (header) | 21,350 | `order_id` | — |
| `order_details.csv` | Event (detail) | 52,050 | `order_details_id` | `order_id` → orders, `pizza_id` → pizzas |
| `pizzas.csv` | Entity | 96 | `pizza_id` | `pizza_type_id` → pizza_types |
| `pizza_types.csv` | Entity | 32 | `pizza_type_id` | — |
| `data_dictionary.csv` | Lookup / documentation | — | — | not loaded |

`orders.date` + `orders.time` are parsed into a single `order_ts` timestamp
during the join and used as the event-time field. `category` (from
`pizza_types.csv`) is the chosen partition key — see §4.

> **Note:** `config.py`'s docstring mentions an earlier 48,620-row snapshot of
> `order_details.csv`. The dataset currently in `Datasets/` has **52,050**
> order-detail rows / 21,350 orders. This README and the Session 1 submission
> document report the actual, currently-measured figures.

## 4. Partitioning Strategy (summary)

- **Chosen key:** `category` (from `pizza_types.category`)
- **Distinct values:** 4 — Classic, Supreme, Veggie, Chicken
- **Skew ratio:** 1.35 : 1 (max 15,487 / min 11,473 rows) — low compared to
  alternatives such as `pizza_id` (61.27 : 1) or `size` (327.08 : 1)
- **Why:** `category` survives the full join path (`order_details → orders →
  pizzas → pizza_types`), is owned by the smallest/most stable dimension
  table, and produces evenly sized, independent aggregation units.
- **Configured parallelism:** `repartition(partitions, "category")` with
  `spark.sql.shuffle.partitions = 8`; benchmarked at 2, 4, and 8 partitions
  (default/chosen = 4, matching the number of distinct category values).

Full detail, including the entity-relationship diagram and the guide-question
analysis, is in the Session 1 submission document.

## 5. How to Run

Run the scripts in this order from inside `Pizza-Flow/`:

```bash
# 1. Profile the raw files (schema, keys, referential integrity)
python profile_files.py

# 2. Build and validate the joined working dataset (pandas)
python load_and_join.py

# 3. (Optional) Evaluate candidate partition keys
python partition_strategy.py

# 4. Run the sequential (pandas) baseline
python sequential_baseline.py

# 5. Run the PySpark parallel implementation + correctness validation
python parallel_compute.py

# 6. Analyze key-level skew and physical Spark partition balance
python partition_analysis.py

# 7. Benchmark sequential vs. 2/4/8-partition Spark runs
python benchmark.py

# 8. (Optional) Regenerate the entity-model and architecture diagrams
python render_diagrams.py
```

Each script can also be run independently — most read whatever inputs they
need from `Datasets/` or `results/` and rebuild the working dataset in memory
if a cached `results/*.parquet`/`.csv` file isn't already present.

## 7. Headline Results (from the captured run)

- **Sequential baseline (pandas):** median **0.0146 s** over 5 runs, 4 groups
- **Spark, 2 partitions:** median **0.4292 s**
- **Spark, 4 partitions:** median **0.3478 s** ← best Spark setting
- **Spark, 8 partitions:** median **0.3597 s**
- **Join strategy:** all 3 joins are broadcast hash joins (0 shuffle/sort-merge)
- **Correctness:** parallel output matches the sequential baseline exactly on
  integer metrics and within `1e-6` tolerance on floating-point metrics
  (`validation_report.json` → `"passed": true`)

At this data size (52,050 rows), Spark's fixed session/task overhead outweighs
the benefit of parallelism — the pandas baseline is faster in absolute terms.
The Spark implementation still demonstrates correct, explicitly bounded
parallel execution and validated results, which is the goal of Session 1.

## 8. Known Limitations

- Only 4 distinct `category` values caps meaningful category-based
  parallelism at 4 partitions; requesting more (e.g. 8) leaves partitions
  empty rather than improving throughput.
- The entity-model and architecture diagrams currently generated by
  `render_diagrams.py` still label the dataset with the older 48,620-row
  figure and should be regenerated to reflect the current 52,050-row data.
- Machine specs used for benchmarking (CPU, cores, RAM) and the exact PySpark
  version installed are not yet recorded — add these for reproducibility.
